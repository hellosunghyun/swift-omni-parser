> 후속 최종 상태: [32개 테스트·대용량·QoS 검증](LOCAL_REVIEW_2026-10-27.md). 아래는 각 작업 당시의 기록입니다.

> 이 문서는 최초 공개 초안 검토 이력입니다. 후속 작업으로 XCTest 타깃·샘플·고지를 추가하고 실제 실행했습니다. 기본 의존성의 XLS 실패는 이후 수정했으며 현재 결과는 [XLS 수정·전환 결과](XLS_CHART_FIX.md)를 참고하세요. CI·배포 바이너리의 남은 제약은 별개입니다.

검토일: 2026년 10월 26일. 기준 소스 커밋: `2d032502ee15b61db967de562339007db2311eed`.

## 판단

독립 Swift Package로 소비할 수 있는 구조이며 공개 API·옵션·의존성 고지의 기본 틀은 있습니다. 다만 현재는 **공개 초안(Draft)**으로 분류하는 것이 적절합니다. 자동 CI, 회귀 테스트, 안정 버전 릴리스와 네이티브 바이너리의 재현·전이 고지 검증이 준비되지 않아 실서비스 도입 준비가 끝났다고 판단하지 않습니다.

검토에서는 공개 저장소 상태, Swift 코드의 주요 입력·형식·이미지 처리 경로, 패키지 명세, 원래 라이선스, 정적 아카이브 멤버와 재빌드 스크립트를 확인했습니다. 새 기능 테스트·실기기 실행·성능 측정은 수행하지 않았습니다.

## 우선순위가 높은 개선점

### 1. 네이티브 바이너리의 고지·소스 대응을 재현 가능한 제작 과정으로 확정

- **확인:** 직접 의존성 다섯 항목의 라이선스 표기와 고정 커밋의 원문은 일치합니다.
- **확인:** 기존 Rust 표준 라이브러리 HTML의 외부 크레이트 목록이 비어 있지만, 기기용 OfficeOxide 아카이브에는 `libc`, `gimli`, `miniz_oxide`, `compiler_builtins` 등의 오브젝트 이름이 존재합니다.
- **영향:** 기존의 MIT·Apache와 상위 크레이트 고지만으로 모든 정적 구성요소의 고지까지 갖췄다고 말할 수 없습니다.
- **이번 보완:** Rust 1.97.1 소스의 관련 원래 고지를 추가 보존하고 아카이브 이름 관찰·출처·파일별 해시를 기록했습니다. 버전까지 일치하는지는 재현 빌드 전에는 확정하지 않습니다.
- **다음 작업:** Rust·SDK·타깃·빌드 옵션을 고정하고, 실제 타깃별 의존성 목록·고지·아카이브 해시를 같은 빌드에서 생성해야 합니다. OpenDocument.core의 배포 자산도 대응하는 전이 구성요소와 소스 취득 경로의 대조가 필요합니다.

근거: `ThirdParty/OfficeOxide/RustStandardLibrary/COPYRIGHT-library.html`, `ADDITIONAL_NOTICE_PROVENANCE.json`, `Documentation/LICENSE_REVIEW.md`.

### 2. LGPL·MPL 의존성이 선택 가능하지 않다는 점을 명확히 안내

- **확인:** `Package.swift`의 단일 `OmniParser` 타깃은 CoreHwp·OdrCore·OfficeOxide를 필수 의존성으로 선언합니다.
- **영향:** PDF만 호출하거나 OCR을 끄는 옵션으로 패키지의 HWP·Office 의존성을 제외할 수 없습니다. 사용자는 자기 코드가 MIT라는 사실과 소비 앱의 배포 조건을 별도로 이해해야 합니다.
- **이번 보완:** README와 라이선스 검토에 필수 의존성이라는 점을 명시했습니다.
- **설계 검토안:** 전체 형식을 제공하는 기존 제품을 유지하면서, 허용적 라이선스의 경량 기능만 소비할 수 있는 별도 제품을 제공할지 검토할 수 있습니다. 이는 모듈 경계·API 설계가 달라지는 작업이므로 이번에는 구현하지 않았습니다.

근거: `Package.swift:24`, `Package.swift:27`, `Documentation/LICENSE_REVIEW.md`.

### 3. 독립 패키지 기준의 CI·회귀 테스트를 먼저 확보

- **확인:** 테스트 타깃·샘플이 없고 GitHub Actions 워크플로도 0개입니다. 공개 태그·릴리스도 없습니다.
- **영향:** 사용자가 파싱 결과와 향후 수정의 회귀 여부를 독립적으로 검증하기 어렵습니다. 현재 로컬 빌드 통과는 결과 정확도·취소·메모리·손상 입력 검증을 대신하지 않습니다.
- **권장 순서:** iOS 패키지 빌드 CI → URL/Data·옵션·배치·부분 실패 회귀 → 출처를 확인한 형식별 샘플 → OCR·대용량·실기기 검증 → 버전 태그.
- **주의:** 이전 앱 저장소의 과거 테스트 결과를 새 패키지의 현재 실행 결과로 표시하면 안 됩니다. CI와 테스트는 이번 검토에서 새로 추가하거나 실행하지 않았습니다.

근거: `Package.swift`, `.github/workflows` 부재, GitHub tags/releases 목록, `Documentation/BUILD_STATUS.md`.

### 4. Office의 OCR 실패가 정상 이미지 추출까지 막는 경로 수정

- **코드 확인:** `DocumentOfficeParseContext.appendImage`는 이미지 디코딩 후 OCR을 먼저 수행하고, 성공해야 `retainImage`를 실행합니다.
- **조건:** `extractImages`와 `performOCR`이 모두 켜져 있고, 디코딩은 성공했지만 OCR이 오류를 던지는 경우입니다.
- **결과:** 경고만 남고 정상 디코딩한 이미지의 PNG 보관 단계도 건너뜁니다. 반면 `DocumentRasterParser.parseImage`는 PNG를 먼저 보관해 OCR 실패 뒤에도 이미지를 유지합니다.
- **개선:** 이미지 보관과 OCR의 실패 처리를 분리하고, 두 옵션이 켜진 경우 OCR 실패 후 PNG가 남는 회귀 사례를 추가해야 합니다.
- **확인 수준:** 코드 경로를 확인한 결과입니다. 이번 검토에서 오류를 주입한 실행 재현은 하지 않았으며 구현도 변경하지 않았습니다.

근거: `Sources/OmniParser/Office/Backend/DocumentOfficeParseContext.swift:133`, `Sources/OmniParser/Images/DocumentRasterParser.swift:85`.

### 5. 구조 해석 실패 후 일반 텍스트 복구를 결과에서 구분

- **코드 확인:** JSON 파싱 실패, XMLParser 실패, RTF 변환 오류에서 일반 텍스트 블록으로 복구합니다.
- **코드 확인:** `DocumentTextParser`는 초기 경고 배열을 비워 두므로, 이 복구만 일어난 경우 구조 추출 실패 경고가 남지 않습니다.
- **영향:** 호출자가 정상 구조 추출과 원문 텍스트 복구를 구별하기 어렵습니다.
- **개선:** 복구 시 위치가 있는 경고를 반환하도록 결과 경로를 바꾸고 손상 JSON/XML/RTF 사례를 검증해야 합니다. 이번에는 구현을 변경하지 않았습니다.

근거: `Sources/OmniParser/Text/Structured/DocumentStructuredTextParser.swift:21`, `:55`, `:64`, `Sources/OmniParser/Text/DocumentTextParser.swift:32`.

## 배포·유지보수 개선

### 바이너리 크기와 재빌드

- OfficeOxide XCFramework가 약 84MiB이고 Simulator 아카이브 하나가 약 56MiB입니다. GitHub 권장 파일 크기 경고가 발생한 구성입니다.
- 버전이 고정된 Release 자산과 SwiftPM 체크섬을 사용하면 소스 이력에서 바이너리 증식을 줄일 수 있습니다. 이전 커밋의 바이너리까지 없어지는 것은 아니므로 공개 이력 재작성은 별도로 판단해야 합니다.
- 기존 바이너리 제작 설명에는 Rust 1.97.1·`RUSTC_BOOTSTRAP`·`build-std`가 있지만 현재 `build.sh`는 이를 고정하지 않습니다. 스크립트는 재빌드 후 `SHA256SUMS`와 고지를 갱신하지도 않습니다. 같은 바이너리가 재현된다고 보장할 수 없습니다.

근거: `ThirdParty/OfficeOxide/README.md`, `ThirdParty/OfficeOxide/build.sh:12`, `SHA256SUMS`.

### 문서와 도입 조건

- README에 Draft 상태와 불안정한 API·의존성·검증 상태를 표시했습니다.
- RTF는 현재 Foundation의 본문 문자열만 추출합니다. RTF 표·삽입 이미지·이미지 OCR은 구현하지 않아 형식 표를 분리해 명시했습니다.
- iOS 27.0과 Swift tools 6.2·언어 모드 5.0의 의미를 유지해야 합니다. 더 넓은 플랫폼 지원은 현재 검증 결과에 포함하지 않습니다.
- 직접 의존성의 `exact` 고정은 검토한 버전을 유지하는 장점이 있지만 소비 프로젝트와 버전 충돌이 날 수 있습니다. 버전 정책과 업데이트 시 검증 절차를 문서화할 필요가 있습니다.
- 일반적인 오픈소스 소비자를 넓게 받으려면 영어 README도 도움이 됩니다. 현재 한국어 문서를 임의로 교체하지 않았습니다.

### 기여·보안 제보

- CONTRIBUTING, SECURITY, 이슈·PR 템플릿이 없습니다. 빌드 환경과 변경 검증 방법, 유지보수 범위부터 간단히 안내하는 것이 좋습니다.
- 문서 파서는 민감한 파일을 다루므로 보안 제보와 재현 샘플 제출 시 공개 이슈에 실제 개인 문서가 올라가지 않도록 경로와 기준을 정할 필요가 있습니다.
- GitHub community profile 점수는 보조 지표일 뿐 실제 코드 품질이나 안전성의 검증값으로 사용하지 않습니다.

## 이번에 수정한 범위

1. README의 Draft 표시, RTF 구현 범위와 필수 의존성 안내
2. 라이선스 검토 문서의 완료 판단·확인 범위 정정
3. Rust 표준 라이브러리 관련 원래 고지와 출처·해시 보충
4. 이 검토 보고서 추가

파서 Swift 소스, 공개 API, 지원 형식의 구현, 패키지 의존성·최소 OS·언어 모드는 변경하지 않았습니다. 원래 라이선스 파일도 대조 후 그대로 보존했습니다.

## 결론

자체 Swift 코드를 MIT로 표시하고 외부 의존성의 원래 조건을 유지하는 구분은 적절합니다. 그러나 루트 LICENSE와 직접 의존성의 표기가 맞는다는 사실만으로 네이티브 바이너리·최종 소비 앱의 재배포 조건까지 모두 충족했다고 결론 낼 수는 없습니다.

공개 초안으로서 다음 우선순위는 **재현 빌드와 라이선스 고지의 대응 확인, CI·회귀 테스트, 확인한 부분 실패 경로 수정, 버전 릴리스**입니다.
