# Ream 위치·경고 API 호환성 검토

2026-10-26. 구현 변경을 적용한 문서가 아니라, 현재 어댑터와 실제 결과를 기준으로 한 변경안이다. **기존 공개 타입과 호출 방식은 유지할 수 있지만, 기존 결과와 완전 일치시키는 것은 별개다.** 원래 엔진의 누락과 오답을 다시 만드는 방향은 권장하지 않는다.

## 유지할 수 있는 계약

DocumentInput, parse/parseBatch 호출, 기본 이미지/OCR false, DocumentParseResult의 블록 기반 fullText, DocumentLocation, DocumentWarningCode를 유지할 수 있다. Ream의 내부 손실·앵커는 어댑터에서 이 모델로 변환한다. 새 공개 모델이나 추가 패키지가 필수는 아니다. 실제 배치 순서·부분 실패·옵션 조합은 앞선 실험에서 검증했지만 모든 자원 제한이 동일하게 적용되는 것은 아니다.

| 항목 | 가능한 변경 | 할 수 없거나 먼저 해결할 부분 |
|---|---|---|
| Word part | 기존 WordDocument와 원본 파트의 명확한 대응을 형식별 매핑에 둠 | 각주·헤더를 문서 본문 part 하나로 뭉개지 않음. 여러 표를 같은 문자열로 강제해 식별성을 잃지 않음 |
| 시트·셀 | 실제 시트 이름, 1-based 행/열, 제공 가능한 병합 span 유지 | chart cache 혼입을 reader에서 먼저 수정. 중복 제거만으로는 잘못된 값/좌표를 복구하지 못함 |
| 슬라이드 | slide[n]의 안정적 식별과 실제 page 번호 보존 | 기존 page=nil에 맞추려고 실제 위치를 지우지 않음. 슬라이드/도형 원본 앵커가 없는 FlowDoc 요소에는 좌표를 추정해서 넣지 않음 |
| bounds | 제공된 원본 변환을 좌상단 기준으로 변환하고 유한값·크기·페이지 좌표계를 검사 | 현재 PPTX/Word adapter에 없는 원본 도형 좌표는 문자열 part 변경만으로 만들 수 없음. 페이지 밖 요소의 처리 기준은 별도 정의 필요 |
| 이미지 ID·위치 | 원본 관계/파트·배치로 결정적인 ID를 만들고 기존 위치 모델을 사용 | PNG 해시만 ID로 쓰면 같은 그림의 여러 배치를 합칠 수 있음. native 결과와 모든 ID를 맞춘다는 보장도 없음 |
| 읽기 순서 | 블록 순서와 fullText 일관성 유지. 원본 문단·시트 주소·슬라이드의 순서를 근거로 지정 | 단순 재정렬로 중복 chart 값이나 원본 요소 누락을 해결하지 못함 |
| fullText·셀 표시 | 입력 서식과 원시 값/표시 값의 정책을 명시하고 정확한 기대값으로 검사 | 통화·백분율·General 정밀도·목록 마커의 선택 없이 숫자/마커를 일괄 제거하는 것은 의미 변경 |

현재 11개 진단 문서에서 행/열/페이지 인덱스와 bounds의 기본 형식 오류는 발견하지 않았다. 이것은 좌표가 실제 원본 요소를 정확히 가리킨다는 증거가 아니다. XLS 차트 셀은 양수 주소여도 잘못된 값이며 Ream에서는 중복된다.

## 경고 매핑

현재 Ream 어댑터는 reader loss를 feature·severity의 일반 문장으로 바꾸고 Swift에서 전부 uncertainReadingOrder로 매핑한다. 이는 정확한 손실 분류가 아니다. Ream Loss는 feature/severity/detail/선택적 where를 제공하지만, reader 전체에 대한 포괄적 loss도 있어 요소별 위치가 없는 경우가 있다.

다음과 같이 **실제 원인이 확인된 경우에만** 기존 코드를 사용한다.

| 확인된 원인 | 기존 코드 |
|---|---|
| 원본 요소는 지원하지만 개별 추출/디코딩에 실패 | extractionFailed |
| 실제 OCR 요청 실패 | imageOCRFailed |
| 측정한 개수·픽셀·작업·할당/해제 예산 때문에 중단 | resourceLimitReached |
| 외부 관계임이 확인돼 자동 읽기를 생략 | externalImageSkipped |
| 해당 요소를 현재 구현이 지원하지 않음 | unsupportedElement |
| 원본 컨테이너/요소가 잘못된 것을 확인 | malformedContent |
| 실제 읽기 순서를 확정하지 못함 | uncertainReadingOrder |

severity만 보고 dropped를 모두 extractionFailed로 바꾸거나, detail 문장에 대한 정규식으로 오류 종류를 추측하지 않는다. reader에서 구조화된 원인과 위치를 확보하거나, 확보하지 못한 한계를 명시한다. 문서 본문을 포함할 수 있는 raw detail/where를 경고·로그로 무조건 전달하지 않는다. 없는 위치를 만들어 넣지 않으며, 위치 없는 포괄 loss를 정밀 경고 구현 완료로 처리하지 않는다.

## 적용 순서 제안

1. 원본 정답 기반 XLS 차트 테스트를 통과시킨다. 기존 엔진의 오답도 별도로 추적한다.
2. 내부 JSON 경계에서 원인·원본 part·셀/슬라이드 위치를 명시하고 형식별 매핑 테스트를 추가한다. 공개 타입은 유지한다.
3. 통화/백분율/정밀도·빈 셀·목록·상속 문구 정책을 확정한 뒤 source truth와 API 계약 테스트를 함께 적용한다. 정확한 기존 문자열 일치와 더 정확한 원본 복원을 동시에 보장한다고 하지 않는다.
4. 전체 corpus·옵션·취소/자원 제한을 재실행하고 속도/RSS 악화가 수용 가능한지 판단한다. 기본 엔진 전환은 그 다음이다.

현재 위치·경고 수정은 운영 코드에 반영하지 않았다. [원본 대조 결과](OFFICE_DIFFERENCE_AUDIT.md)와 [회귀 테스트 구성안](REGRESSION_TEST_PLAN.md)을 함께 본다.
